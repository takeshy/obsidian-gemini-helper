# Workflow Nodes

Workflow YAML is usually generated by AI, but users may ask what node to use or how nodes behave. Each node has an `id`, a `type`, type-specific properties, and usually `next` to continue execution.

# Node Categories

- Variables: `variable`, `set` declare and update variables.
- Control: `if`, `decision`, `while` branch or loop. Conditional edges use `true` and `false` labels.
- LLM: `command` runs a Gemini prompt and saves text or generated image output.
- Data: `http`, `json`, `script` call APIs, parse JSON, or run JavaScript.
- Notes: `note`, `note-read`, `note-search`, `note-list`, `folder-list`, `open` operate on vault content.
- Files: `file-explorer`, `file-save` select or save binary/text files.
- Prompts: `prompt-file`, `prompt-selection`, `dialog` ask the user for file, selection, or dialog input.
- Composition: `workflow` runs another workflow as a sub-workflow.
- RAG: `rag-sync` syncs notes to the selected RAG store.
- External: `mcp`, `obsidian-command` call MCP tools or Obsidian commands.
- Utility: `sleep` pauses execution.

# Decision Branching

The `decision` node supports five `decisionType` values, independently of chat models.
Omitting the type preserves existing true/false workflows.

| decisionType | Criteria | Saved value | Routing |
| --- | --- | --- | --- |
| `boolean` (default) | `prompt` instructions | `"true"` or `"false"` string | `trueNext` / `falseNext` |
| `noul` | `prompt` instructions | Probability from 0 to 1 | `>= threshold` follows `trueNext`; default 0.5 |
| `score` | Ordered `criteria` array of descriptions | Raw number from 0 to criteria.length-1, including fractions | `>= threshold` follows `trueNext` |
| `choice` | `criteria` object of choice names and descriptions | Selected choice name | `branches` maps each choice to a node or `end` |
| `batch` | Named `questions` object with mixed types | JSON object keyed by question name | Ordinary `next`; use saved values in subsequent conditions |

`input` is the shared evidence; `prompt` is required for a single question.
Both support `{{variables}}`. `saveTo` names the output variable and is required
for batch decisions. API failures, missing/invalid answers, cancellation, and the
20-second timeout stop execution without selecting a branch or saving partial
batch results. Cloud API charges apply.

Gemini Helper uses its saved API key and fixed `gemini-decision-1` model.
An explicit `model` must be `gemini-decision-1`.

## Score and Noul thresholds

Score `criteria` is an ordered array of at least two nonempty descriptions.
The numeric scale starts at zero; a four-level rubric produces scores from 0 to 3.
`threshold` supports variables; it defaults to the midpoint of the score range.
The raw numeric result is saved even when it is below the threshold.
For Noul, the default threshold is 0.5 and the saved value is the original probability.

```yaml
- id: score_urgency
  type: decision
  decisionType: score
  prompt: "Rate the urgency of this request."
  input: "{{message}}"
  criteria: ["Routine", "Soon", "Today", "Immediately"]
  threshold: 2
  saveTo: urgency
  trueNext: priority_queue
  falseNext: normal_queue
```

## Choice destinations

Choice `criteria` maps at least two names to descriptions. `branches` must contain
exactly the same names, each mapped to a node ID or `end`. An unrecognized choice
is an error; it never becomes an implicit false branch. Destinations are static
node IDs. Criteria can be YAML objects/arrays or JSON strings in the editor.

```yaml
- id: classify
  type: decision
  decisionType: choice
  prompt: "Classify this request."
  input: "{{message}}"
  criteria:
    refund: "Requests a refund"
    support: "Requests technical support"
    other: "Another request"
  branches:
    refund: refund_handler
    support: support_handler
    other: end
  saveTo: category
```

## Multiple questions in one request

Select **Multiple questions** and enter a named `questions` object. Each question
has `type` (boolean, noul, score, or choice), `instructions`, and `criteria` when
required. All questions share the same `input` and are sent in ONE API request.
Question names should be identifiers suitable for variable paths.

```yaml
- id: assess
  type: decision
  decisionType: batch
  input: "{{message}}"
  questions:
    is_refund:
      type: noul
      instructions: "The customer requests a refund."
    request_type:
      type: choice
      instructions: "Classify the request."
      criteria:
        refund: "A refund request"
        other: "Other requests"
    urgency:
      type: score
      instructions: "Rate urgency."
      criteria: ["Routine", "Soon", "Immediately"]
  saveTo: result
  next: check_urgency
- id: check_urgency
  type: if
  condition: "{{result.urgency}} >= 1.5"
  trueNext: priority_queue
  falseNext: normal_queue
```

`result` contains values such as
`{"is_refund":0.99,"request_type":"refund","urgency":1.8}`.
Use `{{result.is_refund}} >= 0.5`, `{{result.request_type}} == refund`, or
`{{result.urgency}} >= 1.5` in later `if` nodes. Batch uses a normal `next` link
and does not require `trueNext` or `falseNext`. Every answer must be valid before
anything is saved or the next node starts.

Contracts: [TypeSafe System One](https://docs.typesafe.ai/api/system-one.md).
The mixed-question pattern is also illustrated in the user's
[Qiita reference](https://qiita.com/koji0705/items/89f4ab89b68eca7ac559).

# Key Nodes

`command` supports `prompt`, optional `model`, `ragSetting` (`__websearch__`, `__none__`, or setting name), `vaultTools` (`all`, `noSearch`, `none`), `mcpServers`, `attachments`, `enableThinking`, `saveTo`, and `saveImageTo`.

`note` writes content with `path`, `content`, `mode` (`overwrite`, `append`, `create`), `confirm`, and `history`. Confirmation defaults to safe behavior.

`note-read` reads a file into `saveTo`; encrypted files trigger a password prompt and cache the password for the session.

`note-list` can filter by folder, recursion, tags, creation or modification window, sort field, sort order, and limit.

`note-search` searches file names or contents and returns matched context.

`folder-list` lists vault folders from a parent folder.

`open` opens a vault file in Obsidian.

`dialog` shows a modal dialog, can render Markdown, can collect text input, and can return selected buttons or options.

`prompt-file` asks the user to select a Markdown file. In hotkey and event runs it can automatically use the active or event file.

`prompt-selection` asks for editor selection. In hotkey runs it uses the current selection or full active file content; in event runs it uses the event file content.

`file-explorer` selects any supported file and returns `FileExplorerData` with path, name, extension, MIME type, content type, and text or Base64 data.

`file-save` saves FileExplorerData or generated binary/text data back to the vault.

`workflow` executes another workflow as a sub-workflow and can pass variables.

`rag-sync` runs a full checksum-based incremental sync of eligible vault content to the named RAG setting, or the currently selected setting when omitted. Its target folders and exclusion patterns are applied. This node can be assigned to the `startup` event to synchronize RAG when Obsidian starts.

`http` sends external requests. Warn users that HTTP nodes can transmit vault data to third-party services.

`json` expects `source` to be a bare variable name, not `{{source}}` interpolation.

`script` runs JavaScript in the workflow sandbox.

`mcp` calls an enabled MCP server tool configured in plugin settings.

`obsidian-command` runs an Obsidian command by command ID and is useful for operations such as encryption workflows.

`sleep` pauses execution for a configured duration.

# Workflow Options

`options.showProgress: false` hides the execution progress modal for hotkey or workflow-list execution. The visual workflow panel always shows progress.

# Skill Workflow Outputs

When invoked from chat through `run_skill_workflow`, every variable whose name does not start with `_` is returned to the chat model. A final `command` node just to display output is unnecessary; put output presentation rules in `SKILL.md`.
